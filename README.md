# 快手短视频热度预测：一个 AUC 0.98 的模型，为什么输给一行 SQL

> 基于 **KuaiRec**（快手官方公开的学术数据集）的短视频热度预测研究。
> 本仓库的重点不是模型精度，而是**怎么验证一个模型到底有没有用**。

## TL;DR

我做了一个「预测明天哪些内容热度仍居前列」的模型，AUC 0.9813，top 20% 命中 77%。
然后加了一个不建模的基线——只按当天点赞数排序取前 20%——命中 77.22%，AUC 0.9842。

**模型没有增量。** 于是我把任务定义换掉，改预测「相对自身的跃升」，
同一套特征下 top 20% 召回 72.48%，基线只有 8.20%，精确率 27.5% vs 3.1%。

| 预测口径 | 模型 AUC | 惯性基线 AUC | top20% 召回（模型 / 基线） | 正样本率 | 结论 |
|---|---|---|---|---|---|
| 次日热度进入当日前 25% | 0.9813 | **0.9842** | 77.01% / 77.22% | 24.9% | **无增量** |
| 相对跃升（≥ 自身近 7 日均值 2 倍） | 0.8814 | 0.4265 | **72.48%** / 8.20% | 7.6% | 提升约 8.8 倍 |

一句话方法论：**先把基线立起来，再谈模型收益。**

## 1. 问题

短视频平台每天要回答：有限的推广资源给谁。

常规做法是看历史热度，但那是事后判断。这个项目想做的是事前预测：

1. **数据治理**：1,253 万条播放日志怎么清洗、分层入库（MySQL）
2. **业务洞察**：完播/快划行为、时长与完播的关系、广告与普通内容的完播鸿沟
3. **建模**：22 维特征 + 时间切分，用 LR / XGBoost 做次日高潜内容圈选

在第 3 步得到的「很漂亮」的结果，引发了后面全部的验证工作。

## 2. 数据

KuaiRec 的特点是提供**全量曝光矩阵**（不只是点击），所以能看到完整的曝光→行为链条。

| 表 | 来源文件 | 规模 | 字段要点 |
|---|---|---|---|
| `play_log` | `big_matrix.csv.gz` | 原始 12,530,806 → 清洗后 12,257,467 | user_id, video_id, 播放时长, 视频时长, 日期, 小时, 完播比 |
| `video_daily` | `item_daily_features.csv.gz` | 343,341 行（10,728 视频 × 63 天） | 视频属性、曝光/播放/完播/点赞等平台计数 |

- 覆盖 7,176 名用户 × 10,728 个视频；播放流 28 天全量曝光，内容×日统计跨 63 天（2020-07-05 ~ 09-05）
- 清洗：剔除时长缺失/无效记录 24.0 万条，并标记完播倍率 ≥10 的异常流 3.3 万条，合计剔除率 **2.2%**
- 建模样本：**279,158** 行，训练 186,423 / 测试 92,735（时间切分，后 14 天）

原始文件体积约 350 MB，**不随仓库分发**，获取方式见 [`data/README.md`](data/README.md)。

## 3. 实验设计

三个实验互为对照，都在 `experiments/` 下。

### 3.1 强基线对照

`baseline_vs_model.py` —— 同一套特征、同一组参数，只把「比较对象」换成零成本的规则。
惯性基线定义为 `naive = 当日点赞用户数`，即按当天点赞量排序。

### 3.2 特征消融

`ablation.py` —— 22 维拆成三组，跑八种组合：

| 组 | 内容 | 维度 |
|---|---|---|
| CONTENT | 时长、是否广告、上传类型、内容标签、星期 | 5 |
| HEAT | 播放用户数、点赞用户数、完播数、点赞率、完播率 | 5 |
| INERTIA | lag1–3、roll7（7 日滚动）、n_prior_days、gap_days | 12 |

### 3.3 评估口径升级

`eval_upgrade.py` —— 把「14 天测试集混排取 top-k」改成**按天分别圈选再汇总**（per-day）。
业务上每天收盘圈一次明天的候选，全局混排在真实场景里没有对应动作。
两种口径差异 < 1pp，但 per-day 才是对的。

## 4. 主要发现

### 4.1 模型在「热度水平」任务上只剩惯性外推

模型 AUC 0.9813，基线 0.9842。拆开特征看原因：22 维里有 **17 维（当日热度 5 + 惯性趋势 12）在描述「这个视频现在有多火」**，
只有 5 维在描述内容本身。

消融给出直接证据：**只留 5 维当日热度就有 AUC 0.9785**，加满 22 维只到 0.9813，多出的 17 维总贡献 **+0.0028**。

模型实际做的是惯性外推，而最优的惯性外推器就是「今天的点赞数」这一个变量本身。

### 4.2 换个任务，模型才显示出价值

标签从「次日热度进前 25%」换成「次日点赞 ≥ 自身近 7 日均值的 2 倍」——这是惯性解释不了的部分。
同特征、同切分：模型 AUC 0.8814，基线 0.4265，top20% 召回 72.48% vs 8.20%。

有个容易搞混的点：`roll7_like` 在这个口径里同时是**标签的分母**，但**不作为预测输入**。
基线把它当预测值，模型只把它当基准——同一个量，用法不同，结果完全相反。
特征表里剔除 `roll7_like` 后 AUC 从 0.8814 掉到 0.8554，说明约 3 个点来自「知道分母」，其余来自真实的趋势识别。

### 4.3 AUC 0.43 不是坏模型，是均值回归

基线 AUC 0.4265，比随机（0.5）还差。这不是 bug，是一个有意义的负向信号：
**已经很热的视频要再翻倍极难，反而沉下去的更容易跃升。**
所以拿「近 7 日均值高」去圈「将要跃升」的候选，等于系统性选错方向，AUC 才会低于 0.5。

「预测谁更热」和「预测谁会突然热」是方向相反的两个任务，不能共用同一套直觉。

### 4.4 一个负结果

内容属性 5 维在跃升口径下 AUC **0.5310**，几乎等于随机；加进全量特征后整体反而下降 0.0005。
也就是说：**模型识别的是趋势拐点的形态特征，不是内容质量**——后者在这个数据上不成立。

另外 `仅惯性 0.8085 + 仅热度 0.6055 ≠ 全量 0.8814`，高出的部分是「昨天在涨 + 今天在加速」的交互项，单组特征表达不了。

## 5. 局限

- **单一平台、单一时间窗**：只有快手，2020 年 7–9 月共 63 天。结论不外推到冷启动或跨平台。
- **无原始视频内容**：数据集只有元数据与内容标签，没有画面和文本，做不了多模态。这也是「内容属性解释力弱」的部分原因。
- **跃升阈值单一**：只用「2 倍」一个阈值，没做 1.5 / 3 倍的敏感性分析。
- **概率未校准**：AUC 只反映排序质量，没检验概率是否可信，补 Brier 分数和可靠性曲线会更完整。
- **全部为离线评估**：没有线上 A/B，任何数字都不代表上线效果。

## 6. 快速开始

```bash
# 1. 依赖
pip install -r requirements.txt

# 2. 数据（见 data/README.md）
#    把 big_matrix.csv.gz 与 item_daily_features.csv.gz 放入 data/raw/

# 3. 数据库
mysql -u root -P 3307 < sql/schema.sql

# 4. 一键复跑：清洗入库 → SQL 指标 → 建模 → 图表
set MYSQL_HOST=127.0.0.1
set MYSQL_PORT=3307
set MYSQL_USER=root
set MYSQL_PASSWORD=
python run_all.py

# 5. 延伸实验（单独运行）
python experiments/eval_upgrade.py      # per-day 口径 + 精确率 + PR 曲线
python experiments/ablation.py          # 八组特征消融
python experiments/plot_ablation.py     # 只读 json 重新出图
```

模型参数固定：XGBoost 500 棵、learning_rate 0.06、max_depth 6、random_state 42。
多次运行间 AUC 有 0.0005–0.0021 的抖动（多线程非确定性），这是说「无增量」而不是「更差」的原因之一。

