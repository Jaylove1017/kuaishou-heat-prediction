# 快手短视频热度预测：一个 AUC 0.98 的模型，为什么打不过一行 SQL

> 基于 **KuaiRec**（快手团队 RecSys 2022 论文公开的学术数据集）的短视频热度预测研究。
> 本仓库的重点不是模型精度，而是**怎么验证一个模型到底有没有用**。

<sub>**English TL;DR** — A churn-style heat-forecasting study on KuaiRec. The XGBoost model reaches AUC 0.9813 but a zero-cost baseline (rank by today's like count) reaches 0.9842 — i.e. **no detectable increment**, which I quantify with a day-level paired bootstrap rather than by eyeballing. Re-defining the target as a *relative breakout* (next-day likes ≥ 2× the video's own 7-day mean) flips the result: top-20% recall 72.48% vs 8.20%. The point of the repo is the evaluation discipline, not the score.</sub>

## TL;DR

我做了一个「预测明天哪些内容热度仍居前列」的模型，AUC 0.9813，按天圈选 top 20% 命中 77.01%。
然后加了一个不建模的基线——只按当天点赞数排序、同样按天圈选 top 20%——命中 77.22%，AUC 0.9842。

**模型没有可检测的增量。** 于是我把任务定义换掉，改预测「相对自身的跃升」，
同一套特征下 top 20% 召回 72.48%，基线只有 8.20%，精确率 27.5% vs 3.1%。

| 预测口径 | 模型 AUC | 惯性基线 AUC | top20% 召回（模型 / 基线） | 正样本率 | 结论 |
|---|---|---|---|---|---|
| 次日热度进入当日前 25% | 0.9813 | **0.9842** | 77.01% / 77.22% | 24.9% | **无可检测增量** |
| 相对跃升（≥ 自身近 7 日均值 2 倍） | 0.8814 | 0.4265 | **72.48%** / 8.20% | 7.6% | 提升约 8.8 倍 |

> 上表全部数字来自同一份 `outputs/exp_eval_upgrade.json`（per-day 口径）。
> 每个数字的出处见 [`outputs/README.md`](outputs/README.md)，那份表格里同时也标注了三份不该被引用的历史产物。

一句话方法论：**先把基线立起来，再谈模型收益。**

## 1. 问题

短视频平台每天要回答：有限的推广资源给谁。

常规做法是看历史热度，但那是事后判断。这个项目想做的是事前预测：

1. **数据治理**：1,253 万条播放日志怎么清洗、分层入库（MySQL）
2. **业务洞察**：完播/快划行为、时长与完播的关系、广告与普通内容的完播鸿沟
3. **建模**：22 维特征 + 时间切分，用 LR / XGBoost 做次日高潜内容圈选

在第 3 步得到的「很漂亮」的结果，引发了后面全部的验证工作。

## 2. 数据

KuaiRec 的特点是提供**全量曝光矩阵**（不只是点击），所以能看到完整的曝光→行为链条。

| 表 | 来源文件 | 规模 | 字段要点 |
|---|---|---|---|
| `play_log` | `big_matrix.csv.gz` | 原始 12,530,806 → 入库 12,290,655（其中有效播放 12,257,467） | user_id, video_id, 播放时长, 视频时长, 日期, 小时, 完播比 |
| `video_daily` | `item_daily_features.csv.gz` | 343,341 行（10,728 视频 × 63 天） | 视频属性、曝光/播放/完播/点赞等平台计数 |

- 覆盖 7,176 名用户 × 10,728 个视频；播放流 28 天全量曝光，内容×日统计跨 63 天（2020-07-05 ~ 09-05）
- 清洗：坏行（列数不符/时长缺失或 ≤0）24.0 万条被丢弃；完播倍率 ≥10 的异常流 33,188 条**保留但打上 `is_valid=0`**，
  业务分析时按需过滤。合计影响 2.2%
- 建模样本：**279,158** 行，训练 186,423 / 测试 92,735（时间切分，后 14 天）

> 「入库行数」和「有效行数」是两个概念，本文出现的 12,290,655 是入库行，12,257,467 是 `is_valid=1` 的行。
> 这两个数在 `outputs/base_metrics.json` 里都能查到。

原始文件体积约 350 MB，**不随仓库分发**，获取方式见 [`data/README.md`](data/README.md)。

## 3. 实验设计

四个实验互为对照，特征与标签的实现统一来自 `src/features.py`（全项目唯一一份）。

### 3.1 主对照：同口径下的模型 vs 零成本规则

`eval_upgrade.py` —— 同一套特征、同一组超参、同一批测试样本，只把比较对象换成规则。

惯性基线定义为 `naive = 当日点赞用户数`：**不建模，只按当天点赞量排序。**

两边都用 **per-day** 评估：每天收盘圈一次明天的候选，再汇总。这是业务上真实存在的动作，
而「把 14 天测试集混在一起取 top-k」在线上没有对应操作。

| Top-k（按天圈选） | 模型召回 | 基线召回 | 召回差 | 模型精确率 | 基线精确率 |
|---|---|---|---|---|---|
| top5% | 19.99% | 19.84% | +0.14pp | 99.74% | 99.03% |
| top10% | 39.88% | 39.56% | +0.33pp | 99.46% | 98.64% |
| top15% | 59.24% | 58.71% | +0.53pp | 98.48% | 97.59% |
| **top20%** | **77.01%** | **77.22%** | **−0.21pp** | 95.99% | 96.25% |
| top25% | 89.91% | 92.36% | −2.45pp | 89.65% | 92.10% |
| top30% | 95.80% | 97.99% | −2.19pp | 79.61% | 81.43% |

**怎么读这张表**：top15% 以内模型有 +0.1~+0.5pp 的微弱优势，top20% 起转负，top25% 后扩大到 −2pp 以上。
问题在于这些差值**全都小于种子抖动**（AUC 抖动 0.0005–0.0021，粗算对应召回抖动 ±0.2pp）。
所以准确的说法是**与一行 SQL 统计上不可区分**，而不是「模型更差」——
差值的置信区间见 `experiments/significance.py`（按天 bootstrap + 5 个种子）。

我选择报这张全 k 表而不是只报 top20，就是为了让人自己判断「0.2pp 算不算差」。

### 3.2 特征消融

`ablation.py` —— 22 维按语义拆成三组，跑八种组合（每组共用同一批样本，否则不可比）：

| 组 | 内容 | 维度 |
|---|---|---|
| CONTENT | 时长、是否广告、上传类型、内容标签、星期 | 5 |
| HEAT | 播放用户数、点赞用户数、完播数、点赞率、完播率 | 5 |
| INERTIA | lag1–3、roll7（7 日滚动）、n_prior_days、gap_days | 12 |

G1–G8 覆盖「单组 / 两两组合 / 全部 / 全部剔除 roll7」，
其中 **G7→G8 是专门为量化标签泄漏设计的**：跃升口径下 `roll7_like` 既是标签分母又是特征，
两组的差就是「模型仅凭记住分母拿到多少分」。

### 3.3 评估口径升级

`eval_upgrade.py` —— 同一批模型输出，同时算全局混排与按天圈选两种口径：

| Top-k | 模型 全局 | 模型 按天 | 差 | 基线 全局 | 基线 按天 | 差 |
|---|---|---|---|---|---|---|
| top20% | 76.25% | 77.01% | +0.76pp | 76.39% | 77.22% | +0.82pp |
| top25% | 87.68% | 89.91% | +2.22pp | 89.24% | 92.36% | +3.12pp |
| top30% | 94.21% | 95.80% | +1.60pp | 96.06% | 97.99% | +1.93pp |

切换口径让两边同时上升 0.8–3.1pp（top20 抬升最小，top25 最大），
**差距方向不变、幅度略扩**（top25 从 −1.56pp 变为 −2.45pp）。
所以结论不依赖口径选择，但 per-day 才是业务上正确的那个——这正是我保留这张表的原因。

## 4. 主要发现

### 4.1 模型在「热度水平」任务上只剩惯性外推

模型 AUC 0.9813，基线 0.9842。拆开特征看原因：22 维里有 **17 维（当日热度 5 + 惯性趋势 12）在描述「这个视频现在有多火」**，
只有 5 维在描述内容本身。

消融给出直接证据：

| 组 | 特征 | 维度 | AUC（绝对热量口径） | AUC（跃升口径） |
|---|---|---|---|---|
| G1 仅内容 | CONTENT | 5 | 0.7465 | 0.5310 |
| G2 仅当日热度 | HEAT | 5 | **0.9785** | 0.6055 |
| G3 仅惯性 | INERTIA | 12 | 0.9707 | **0.8085** |
| G5 内容＋惯性 | — | 17 | 0.9721 | 0.8080 |
| G7 全部 | — | 22 | 0.9813 | 0.8814 |
| G8 全部−roll7 | — | 21 | 0.9808 | 0.8554 |

**只留 5 维当日热度就有 AUC 0.9785，加满 22 维只到 0.9813，多出的 17 维总贡献 +0.0028。**
模型实际做的是惯性外推，而最优的惯性外推器就是「今天的点赞数」这一个变量本身。

### 4.2 换个任务，模型才显示出价值

标签从「次日热度进前 25%」换成「次日点赞 ≥ 自身近 7 日均值的 2 倍」——这是惯性解释不了的部分。
同特征、同切分、同超参：模型 AUC 0.8814，基线 0.4265，**top20% 召回 72.48% vs 8.20%**，精确率 27.5% vs 3.1%。

有个容易搞混的点：`roll7_like` 在这个口径里同时是**标签的分母**，但**不作为预测输入**。
基线把它当预测值，模型只把它当基准——同一个量，用法不同，结果完全相反。

这不是「我觉得」，是量化过的：G7（22 维，含 roll7）AUC 0.8814 → G8（21 维，剔除 roll7）0.8554，
**约 2.6 个点来自「知道分母」**；剔除后仍有 0.8554，说明趋势识别本身贡献了绝大部分。
G5→G6 能在没有当日热度帮忙的条件下再验一次：0.8080 → 0.7773，roll7 贡献 3.1 个点。

### 4.3 AUC 0.43 不是「发现了均值回归」，是构造性的反向

基线 AUC 0.4265，比随机（0.5）还差。

需要先说清楚一件事：**这个数有一部分是恒等式，不是发现。** 标签是 `next_like ≥ 2 × roll7_like`，
而基线排序分就是 `roll7_like`——分母越大越难满足 2 倍。用分母去排序预测这个标签，AUC 必然低于 0.5。

要让「均值回归」成为被数据支持的解释，得看另外两条排序线（`breakout_experiment.py` 的「方向检验」）：

- 按 `1/roll7` 排序（越冷越优先）→ 若均值回归成立，应 > 0.5
- 按 `当日点赞 / roll7` 归一化动量排序 → 应明显强于前两条

只有这两条也成立，才能说「已经很热的视频要再翻倍极难，反而沉下去的更容易跃升」。
业务含义确实存在——**拿「近 7 日均值高」去圈「将要跃升」的候选，等于系统性选错方向**——
但它成立的理由是标签定义本身，把它写成"数据揭示的规律"是过度解读。

「预测谁更热」和「预测谁会突然热」是方向相反的两个任务，不能共用同一套直觉。这句是全文最实的一句。

### 4.4 一个负结果：内容属性几乎不提供增量

内容属性 5 维在跃升口径下 AUC **0.5310**，几乎等于随机。
换成边际增量看更直接：G3（仅惯性 0.8085）→ G5（内容＋惯性 0.8080），**反而下降 0.0005**；
绝对热度口径下 G2（0.9785）→ G4（0.9789），只涨 0.0004。

也就是说：**在已有热度/惯性特征的条件下，内容属性的边际解释力约等于零。**
模型识别的是趋势拐点的形态特征，不是内容质量。

（注意 G1 在绝对热度口径下有 0.7465，说明内容属性单靠自己并非无信息——是"不提供增量"，
不是"没有信息"。两者区别很大，前者才是这个项目要说的。）

另外 `仅惯性 0.8085 + 仅热度 0.6055 ≠ 全量 0.8814`，高出的部分是「昨天在涨 + 今天在加速」的交互项，
单组特征表达不了。

## 5. 局限

- **单一平台、单一时间窗**：只有快手，2020 年 7–9 月共 63 天。结论不外推到跨平台。
- **「次日」不严格是次日**：目标日 `next_d` 取的是该视频下一次出现的日期，
  两次出现之间可能隔几天到几十天（`gap_days`），因此标签窗口长度不统一。
  严格口径（`gap_days == 1`）已在 `src/features.py` 实现（`gap_max=1` / `--strict-gap`），
  但已提交的指标仍是旧口径，重跑后需要同步更新本文数字。
- **冷启动样本不进模型**：22 维含 `lag1–3`，`n_prior_days ≤ 2` 的行在 `dropna` 后必然被删。
  这批恰恰是最需要预测的对象（新视频上「按当日点赞排序」等于瞎猜）。
  `--keep-na` 可保留它们（XGBoost 原生处理缺失值，LR 走中位数填补），但目前没有对应指标。
- **切分按特征日而非目标日**：训练集末尾样本的标签日可能落进测试窗口。
  `--strict-split` 已支持按 `next_d` 切分，同样需要重跑才有数字。
- **标签分位阈值用全期计算**：`label_abs` 的 75 分位在含测试期的样本上算，属轻微跨期泄漏。
  另外口径描述应为「当日**可预测样本**的前 25%」，不等于「当日全部活跃视频的前 25%」。
- **内容特征用整数编码**：`up_type_idx` / `tag_idx` 用 `category.cat.codes`，类别被压成一维乱序数轴，
  会低估内容属性的表达力。`0.5310` 这个数的正确读法是「在当前编码方式下无信号」，
  换 one-hot 后应复核。
- **无原始视频内容**：数据集只有元数据与内容标签，没有画面和文本，做不了多模态。
- **概率未校准**：AUC 只反映排序质量，没检验概率是否可信（Brier / 可靠性曲线未做）。
- **全部为离线评估**：没有线上 A/B，任何数字都不代表上线效果。

已做过的稳健性检验（`outputs/label_robustness.csv`）：

| 跃升标签定义 | 测试样本 | 正样本率 | 模型 AUC | 基线 AUC | 召回（模型 / 基线，全局口径） |
|---|---|---|---|---|---|
| 原始 2 倍阈值 | 92,735 | 7.60% | 0.8814 | 0.4265 | 72.67% / 8.20% |
| 最小量门槛 K=20 | 34,476 | 7.15% | 0.8993 | 0.3146 | 79.36% / 4.87% |
| 泊松显著性（+2σ） | 92,735 | 12.16% | 0.8909 | 0.6412 | 72.77% / 26.52% |

三种定义下模型都对基线保持大幅优势，说明结论不依赖某一个阈值。
**未做**的是 1.5× / 3× 连续阈值的敏感曲线。

## 6. 快速开始

```bash
# 1. 依赖（Python 3.11 或 3.13 验证通过）
pip install -r requirements.txt

# 2. 数据：把两个原始文件放到 data/raw/（约 350 MB，见 data/README.md）
pip install huggingface_hub
huggingface-cli download hiiamkik/kuai-rec-data --repo-type dataset \
  --include "big_matrix.csv.gz" "item_daily_features.csv.gz" --local-dir data/raw

# 3. 数据库（推荐：容器化，端口已对齐 3307）
docker compose up -d
#   或者用已有的 MySQL：
#   mysql -h 127.0.0.1 -P 3307 -u root < sql/schema.sql

# 4. 一键复跑：清洗入库 → SQL 指标 → 建模 → 图表
export MYSQL_HOST=127.0.0.1 MYSQL_PORT=3307 MYSQL_USER=root MYSQL_PASSWORD=
python run_all.py

#   Windows cmd / PowerShell 用：
#   set MYSQL_HOST=127.0.0.1 && set MYSQL_PORT=3307 && set MYSQL_USER=root && set MYSQL_PASSWORD=

# 5. 延伸实验
python experiments/eval_upgrade.py    # per-day 口径 + 精确率 + PR 曲线（本文主表来源）
python experiments/significance.py    # 差值 95%CI + 多种子（判断「无增量」是否成立）
python experiments/ablation.py        # 八组特征消融
python experiments/plot_ablation.py   # 只读 json 重新出图
python experiments/breakout_experiment.py  # 早期口径 + 方向检验

# 6. 测试（不需要数据库和原始数据）
pytest -q
```

模型参数固定：XGBoost 500 棵、learning_rate 0.06、max_depth 6、subsample/colsample 0.9、`random_state=42`，
并发数统一由 `src/features.py` 的 `N_JOBS` 控制（可用环境变量覆盖）。
多次运行间 AUC 有 0.0005–0.0021 的抖动（多线程非确定性）——**所以「无增量」必须靠置信区间说，
不能靠眼看两个小数点。**
