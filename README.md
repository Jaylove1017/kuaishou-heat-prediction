# 快手短视频热度预测：一个 AUC 0.98 的模型，为什么打不过一行 SQL

> 基于 **KuaiRec**（快手团队 RecSys 2022 论文公开的学术数据集）的短视频热度预测研究。
> 本仓库的重点不是模型精度，而是**怎么验证一个模型到底有没有用**。

<sub>**English TL;DR** — A heat-forecasting study on KuaiRec. XGBoost reaches AUC 0.9811, while a zero-cost rule (rank by today's like count) reaches 0.9842. A day-level paired bootstrap puts the AUC gap at −0.0031 [−0.0063, −0.0002] — real but tiny — while the per-day top-20% recall gap (−0.15pp) has a CI that crosses zero. Re-defining the target as a *relative breakout* (next-day likes ≥ 2× the video's own 7-day mean) flips it: 72.67% vs 8.20%. Three follow-up audits quantify what the headline numbers hide: the "next-day" label is literally next-day only 90.1% of the time, `dropna` silently deleted the entire cold-start segment, and adding 12M rows of playback logs *hurt* rather than helped.</sub>

## TL;DR

我做了一个「预测明天哪些内容热度仍居前列」的模型，AUC 0.9811，按天圈选 top 20% 命中 77.05%。
然后加了一个不建模的基线——只按当天点赞数排序、同样按天圈选 top 20%——命中 77.21%，AUC 0.9842。

**模型在排序质量上确实略输（差值 −0.0031，95% CI [−0.0063, −0.0002]，刚好不含 0），
但在「每天圈选 top 20%」这个真实业务动作上，两边不可区分（−0.15pp，CI [−0.69, +0.34]）。**

于是我把任务定义换掉，改预测「相对自身的跃升」，同一套特征下
top 20% 召回 72.67%，基线只有 8.20%，精确率 27.61% vs 3.12%。

| 预测口径 | 模型 AUC | 惯性基线 AUC | top20% 召回（模型 / 基线） | 正样本率 | 结论 |
|---|---|---|---|---|---|
| 次日热度进入当日前 25% | 0.9811 | **0.9842** | 77.05% / 77.21% | 24.9% | 排序略输，头部不可区分 |
| 相对跃升（≥ 自身近 7 日均值 2 倍） | 0.8814 | 0.4265 | **72.67%** / 8.20% | 7.6% | 提升约 8.9 倍 |

> 上表全部数字来自同一份 `outputs/exp_eval_upgrade.json`（per-day 口径），
> 差值区间来自 `outputs/exp_significance.json`（1000 次按天配对 bootstrap × 5 个种子）。
> 每个 json 的出处与被引用位置见 [`outputs/README.md`](outputs/README.md)。

一句话方法论：**先把基线立起来，再谈模型收益。**

## 1. 问题

短视频平台每天要回答：有限的推广资源给谁。

常规做法是看历史热度，但那是事后判断。这个项目想做的是事前预测：

1. **数据治理**：1,253 万条播放日志怎么清洗、分层入库（MySQL）
2. **业务洞察**：完播/快划行为、时长与完播的关系、广告与普通内容的完播鸿沟
3. **建模**：22 维特征 + 时间切分，用 LR / XGBoost 做次日高潜内容圈选

在第 3 步得到的「很漂亮」的结果，引发了后面全部的验证工作。

## 2. 数据

KuaiRec 的特点是提供**全量曝光矩阵**（不只是点击），所以能看到完整的曝光→行为链条。

| 表 | 来源文件 | 规模 | 字段要点 |
|---|---|---|---|

| `video_daily` | `item_daily_features.csv.gz` | 343,341 行（10,728 视频 × 63 天） | 视频属性、曝光/播放/完播/点赞等平台计数 |

- 覆盖 7,176 名用户 × 10,728 个视频；播放流 28 天全量曝光，内容×日统计跨 63 天（2020-07-05 ~ 09-05）
  → **播放流只覆盖 28 天中的 20.3% 的「视频×日」组合**，这一点直接决定了 §4.6 的负结果
- 清洗：坏行（列数不符/时长缺失或 ≤0）24.0 万条被丢弃；完播倍率 ≥10 的异常流 33,188 条**保留但打上 `is_valid=0`**，
  业务分析时按需过滤。合计影响 2.2%

> 这两个数在 `outputs/base_metrics.json` 里都能查到。

原始文件体积约 350 MB，**不随仓库分发**，获取方式见 [`data/README.md`](data/README.md)。

## 3. 实验设计

六个实验互为对照，特征与标签的实现统一来自 `src/features.py`（全项目唯一一份）。

### 3.1 主对照：同口径下的模型 vs 零成本规则

`eval_upgrade.py` —— 同一套特征、同一组超参、同一批测试样本，只把比较对象换成规则。

惯性基线定义为 `naive = 当日点赞用户数`：**不建模，只按当天点赞量排序。**

两边都用 **per-day** 评估：每天收盘圈一次明天的候选，再汇总。这是业务上真实存在的动作，
而「把 14 天测试集混在一起取 top-k」在线上没有对应操作。

| Top-k（按天圈选） | 模型召回 | 基线召回 | 召回差 | 模型精确率 | 基线精确率 |
|---|---|---|---|---|---|
| top5% | 19.98% | 19.84% | +0.14pp | 99.72% | 99.03% |
| top10% | 39.89% | 39.56% | +0.33pp | 99.47% | 98.64% |
| top15% | 59.22% | 58.71% | +0.51pp | 98.44% | 97.59% |
| **top20%** | **77.05%** | **77.21%** | **−0.16pp** | 96.05% | 96.24% |
| top25% | 89.90% | 92.35% | −2.46pp | 89.64% | 92.09% |
| top30% | 95.79% | 97.98% | −2.19pp | 79.59% | 81.42% |

**怎么读这张表**：top15% 以内模型有 +0.1~+0.5pp 的微弱优势，top20% 起转负，top25% 后扩大到 −2.5pp。

关键在于这些差值到底算不算差 —— 这件事不能靠眼看两个小数点，所以做了按天配对 bootstrap：

| 指标 | 差值（模型 − 基线） | 95% CI | 跨 0？ |
|---|---|---|---|
| AUC | −0.0031 | [−0.0063, −0.0002] | 否（**边界显著，基线略优**） |
| per-day top20% 召回 | −0.15pp | [−0.69, +0.34] | 是（**不可区分**） |

跨种子的稳定性：5 个种子下 AUC 差 −0.0031 ± 0.0003（min −0.0036 / max −0.0029），
没有一次翻正 —— 所以「基线在排序上略好」是稳定现象，不是某次运行的偶然。
但它的**幅度只有 0.003**，而业务真正消费的是头部候选，那里两者打平。

> 我原来写的是「统计上与一行 SQL 不可区分」，这个说法**过头了**：CI 上界 −0.0002 虽然紧贴 0，
> 但确实不含 0。准确表述是「AUC 上基线小幅但显著地更好，头部圈选上不可区分」。

### 3.2 特征消融

`ablation.py` —— 22 维按语义拆成三组，跑八种组合（每组共用同一批样本，否则不可比）：

| 组 | 内容 | 维度 |
|---|---|---|
| CONTENT | 时长、是否广告、上传类型、内容标签、星期 | 5 |
| HEAT | 播放用户数、点赞用户数、完播数、点赞率、完播率 | 5 |
| INERTIA | lag1–3、roll7（7 日滚动）、n_prior_days、gap_days | 12 |

G1–G8 覆盖「单组 / 两两组合 / 全部 / 全部剔除 roll7」，
其中 **G7→G8 是专门为量化标签泄漏设计的**：跃升口径下 `roll7_like` 既是标签分母又是特征，
两组的差就是「模型仅凭记住分母拿到多少分」。

### 3.3 评估口径升级

`eval_upgrade.py` —— 同一批模型输出，同时算全局混排与按天圈选两种口径：

| Top-k | 模型 全局 | 模型 按天 | 差 | 基线 全局 | 基线 按天 | 差 |
|---|---|---|---|---|---|---|
| top20% | 76.28% | 77.05% | +0.77pp | 76.39% | 77.21% | +0.82pp |
| top25% | 87.60% | 89.90% | +2.30pp | 89.26% | 92.35% | +3.09pp |
| top30% | 94.08% | 95.79% | +1.71pp | 96.05% | 97.98% | +1.93pp |

切换口径让两边同时上升 0.8–3.1pp（top20 抬升最小，top25 最大），
**差距方向不变、幅度略扩**（top25 从 −1.66pp 变为 −2.46pp）。
所以结论不依赖口径选择，但 per-day 才是业务上正确的那个——这正是我保留这张表的原因。

### 3.4 显著性检验

`significance.py` —— 「无增量」如果只靠「两个小数点看起来差不多」来论证，读者无法自己判断。

做法：
1. **按天配对 bootstrap 1000 次** —— per-day 口径下「天」才是独立单元；按样本重采样会把
   同一天内高度相关的样本当成独立信息，区间会被严重低估。同一次重采样里同时算模型和基线，
   保持两者相关性，才是配对比较。
2. **5 个随机种子** —— 报均值 ± 标准差，看差值会不会翻正。

### 3.5 口径审计

`strict_eval.py` —— README 里三句「说得很顺但其实没验过」的话，各自量化一次：
严格次日（`gap_days == 1`）、保留冷启动样本、按目标日切分。四种配置跑同一套代码：

| 配置 | gap 限制 | 是否 dropna | 切分依据 |
|---|---|---|---|
| A 默认（历史口径） | 不限 | 是 | 特征日 `d` |
| B 严格次日 | ≤ 1 天 | 是 | 特征日 `d` |
| C 保留冷启动 | 不限 | 否 | 特征日 `d` |
| D 严格次日 + 按目标日 | ≤ 1 天 | 否 | 目标日 `next_d` |

### 3.6 播放日志特征

`playlog_features.py` —— 1229 万条播放日志此前**一行都没进过模型**，只用于 SQL 分析。
这个实验检验「模型打不过 SQL，是不是因为它压根没看到内容质量信号」。

## 4. 主要发现

### 4.1 模型在「热度水平」任务上只剩惯性外推

模型 AUC 0.9811，基线 0.9842。拆开特征看原因：22 维里有 **17 维（当日热度 5 + 惯性趋势 12）在描述「这个视频现在有多火」**，
只有 5 维在描述内容本身。

消融给出直接证据：

| 组 | 特征 | 维度 | AUC（绝对热量口径） | AUC（跃升口径） |
|---|---|---|---|---|
| G1 仅内容 | CONTENT | 5 | 0.7426 | 0.5284 |
| G2 仅当日热度 | HEAT | 5 | **0.9786** | 0.6065 |
| G3 仅惯性 | INERTIA | 12 | 0.9711 | **0.8084** |
| G5 内容＋惯性 | — | 17 | 0.9721 | 0.8090 |
| G7 全部 | — | 22 | 0.9811 | 0.8814 |
| G8 全部−roll7 | — | 21 | 0.9812 | 0.8555 |

**只留 5 维当日热度就有 AUC 0.9786，加满 22 维只到 0.9811，多出的 17 维总贡献 +0.0025。**
模型实际做的是惯性外推，而最优的惯性外推器就是「今天的点赞数」这一个变量本身。

顺带一个细节：绝对热度口径下 G7→G8 是 **0.9811 → 0.9812，剔除 roll7 反而微升**。
因为这条线里 `like_user_num` 与 `roll7_like` 高度共线，去掉一个只是让模型少了个冗余变量。
roll7 的真正作用在跃升口径里（见 §4.2）。

### 4.2 换个任务，模型才显示出价值

标签从「次日热度进前 25%」换成「次日点赞 ≥ 自身近 7 日均值的 2 倍」——这是惯性解释不了的部分。
同特征、同切分、同超参：模型 AUC 0.8814，基线 0.4265，**top20% 召回 72.67% vs 8.20%**，精确率 27.61% vs 3.12%。
这个差距的 95% CI 是 [+62.38, +66.51]pp（AUC 差 [+0.4420, +0.4674]），跟「不可区分」完全不是一回事。

有个容易搞混的点：`roll7_like` 在这个口径里同时是**标签的分母**，但**不作为预测输入**。
基线把它当预测值，模型只把它当基准——同一个量，用法不同，结果完全相反。

这不是「我觉得」，是量化过的：G7（22 维，含 roll7）AUC 0.8814 → G8（21 维，剔除 roll7）0.8555，
**约 2.6 个点来自「知道分母」**；剔除后仍有 0.8555，说明趋势识别本身贡献了绝大部分。
G5→G6 能在没有当日热度帮忙的条件下再验一次：0.8090 → 0.7769，roll7 贡献 3.2 个点。

### 4.3 AUC 0.43 不是「发现了均值回归」，是构造性的反向

基线 AUC 0.4265，比随机（0.5）还差。

需要先说清楚一件事：**这个数有一部分是恒等式，不是发现。** 标签是 `next_like ≥ 2 × roll7_like`，
而基线排序分就是 `roll7_like`——分母越大越难满足 2 倍。用分母去排序预测这个标签，AUC 必然低于 0.5。

要让「均值回归」成为被数据支持的解释，得看另外两条排序线（`breakout_experiment.py` 的「方向检验」）：

| 排序线 | AUC | top20% 召回 | 说明 |
|---|---|---|---|
| 按 `roll7`（分母越大越难跃升） | 0.3381 | 8.56% | 构造性反向，不算发现 |
| 按 `1/roll7`（越冷越优先） | 0.6619 | 42.05% | 均值回归**确实存在**，但没有想象中强 |
| 按 `当日点赞/roll7` 归一化动量 | 0.7042 | 62.19% | 比单看冷启动强得多 |
| 22 维模型 | **0.8814** | **72.67%** | 仍显著高于前两条 |

四条线放一起才说得清：均值回归是真的（0.6619 > 0.5），动量更强（0.7042），
但模型 0.8814 明显超过两者 —— **模型不是只会「越冷越押」**。这比单看 0.4265 诚实得多。

业务含义确实存在——**拿「近 7 日均值高」去圈「将要跃升」的候选，等于系统性选错方向**——
但它成立的理由是标签定义本身，把它写成"数据揭示的规律"是过度解读。

「预测谁更热」和「预测谁会突然热」是方向相反的两个任务，不能共用同一套直觉。这句是全文最实的一句。

### 4.4 一个负结果：内容属性几乎不提供增量

内容属性 5 维在跃升口径下 AUC **0.5284**，几乎等于随机。
换成边际增量看更直接：G3（仅惯性 0.8084）→ G5（内容＋惯性 0.8090），**只涨 0.0006**；
绝对热度口径下 G2（0.9786）→ G4（0.9792），同样只涨 0.0006；
G3（仅惯性 0.9711）→ G5（内容＋惯性 0.9721）涨 0.0010。

也就是说：**在已有热度/惯性特征的条件下，内容属性的边际解释力约等于零。**
模型识别的是趋势拐点的形态特征，不是内容质量。

（注意 G1 在绝对热度口径下有 0.7426，说明内容属性单靠自己并非无信息——是"不提供增量"，
不是"没有信息"。两者区别很大，前者才是这个项目要说的。）

另外 `仅惯性 0.8084 + 仅热度 0.6065 ≠ 全量 0.8814`，高出的部分是「昨天在涨 + 今天在加速」的交互项，
单组特征表达不了。

### 4.5 三个口径审计：HEADLINE 数字背后藏着什么

这一节是新增的。原文对三件事都是「已实现开关，需要重跑才有数字」——现在跑完了。

**（1）「次日」确实基本是次日，但不是 100%**

`next_d` 是「该视频下一次出现的日期」而非 `d+1`。实测目标间隔 `lead_days = next_d − d` 的分布：

| 指标 | 值 |
|---|---|
| 中位数 / P90 | 1 天 / 1 天 |
| `lead_days == 1` 的样本占比 | **93.01%** |
| `lead_days ≤ 7` 的占比 | 95.70% |
| 最大间隔 | 179 天 |

所以「次日」这个词**基本站得住**（九成三样本真的是次日），但剩下 7% 里最长隔了 179 天。
只保留严格次日时（配置 B）：样本 279,158 → 259,069，AUC 0.9811 → 0.9799，
top20% 召回 77.05% → 77.26%。**几乎不变**，模型依然略输基线（−0.0036）。

> 这里踩过一个坑，值得记下来：`gap_days` 是「距**上**一次观测多久」（向后，合法特征），
> `lead_days` 才是「距**标签日**多远」（向前）。一开始我用 `gap_days ≤ 1` 做严格次日过滤，
> 结果把所有首观测行（其 `gap_days` 被填成哨兵值 99）连根删掉 —— 严格口径下冷启动段凭空消失。
> 两个量方向相反，代码里现在分开命名，测试锁住。

**（2）冷启动样本被 `dropna` 删光了，而它恰恰是最该预测的一段**

22 维含 `lag1–3`，`n_prior_days ≤ 2` 的行必然有缺失，`dropna` 后整段消失。
实测：309,522 行有标签的样本里，**30,364 行（9.81%）被删掉**，
而这一段的正样本率是 **33.41%**，比老视频的 24.11% 高出 9.3pp —— 新内容更容易冲上热榜，
**信息量最大的一段被扔了**。

保留它们（配置 C，XGBoost 原生吃 NaN）：

| 历史长度 | 样本数 | 段内 top20% 召回 |
|---|---|---|
| 首次活跃（0 天） | 2,243 | **43.84%** |
| 1–2 天 | 3,694 | **62.91%** |
| 3–6 天 | 5,220 | 55.53% |
| 7 天以上 | 87,515 | 77.93% |

新视频上「按当日点赞排序」等于瞎猜，模型能拿到 43.84% / 62.91% —— 这里才是模型真正有价值的地方，
而它在默认口径里完全不可见。

**（3）按特征日切分确实有轻微泄漏**

配置 A 的训练集里有 **7,105 行**样本，特征日 ≤ split 但目标日 > split，标签落在测试窗口内。
换成按目标日切分（配置 D，泄漏 0 行）后：AUC 0.9811 → 0.9757（**−0.0054**），
top20% 召回 77.05% → 74.84%。

四种配置全表：

| 配置 | 样本 | 测试 | AUC 模型/基线 | top20% 模型/基线 | 训练集标签跨界行数 |
|---|---|---|---|---|---|
| A 默认 | 279,158 | 92,735 | 0.9811 / 0.9842 | 77.05% / 77.21% | 7,105 |
| B 严格次日 | 259,069 | 82,875 | 0.9799 / 0.9835 | 77.26% / 77.60% | 6,104 |
| C 保留冷启动 | 309,522 | 98,672 | 0.9779 / 0.9802 | 74.53% / 75.23% | 7,261 |
| D 严格次日＋按目标日＋保留冷启动 | 287,886 | 94,392 | 0.9757 / 0.9795 | 74.84% / 75.76% | 0 |

**所有配置下「模型略输基线」这个方向都没变**，AUC 差在 −0.0023 ~ −0.0038 之间，
top20% 召回差在 −0.16pp ~ −0.92pp 之间。这是本文最稳的一个结论：
**把「次日」的严格性、冷启动样本、切分泄漏这三个问题全修掉之后，结论没有被推翻，只是幅度更清楚了。**

### 4.6 一个被证伪的假设：1229 万条播放日志加进来，反而更差

我原先的判断是：模型打不过 SQL，是因为 `video_daily` 只有「多少人播、多少人赞」的总量，
没有「这些人看得怎么样」的分布，所以模型拿不到内容质量信号。
`play_log` 里恰好有最经典的那几个 —— 完播率分布、快看率、重复观看率。

于是把 1229 万行按 (视频, 日) 聚合成 7 个分布特征（`wr_p50`、`wr_p90`、快看率、看完率、
重复观看率、log 播放数、去重用户占比），加进 22 维重跑：

| 组 | 维度 | 绝对热度 AUC | top20% 召回 | 跃升 AUC | top20% 召回 |
|---|---|---|---|---|---|
| G0 基线 22 维 | 22 | 0.9811 | 77.05% | 0.8814 | 72.67% |
| G1 ＋播放分布 | 29 | **0.9750（−0.0061）** | **76.13%（−0.92pp）** | 0.8818 | 73.05% |
| G2 ＋显式比率 | 25 | 0.9805 | 77.04% | 0.8832 | 73.09% |
| G3 全部 | 32 | 0.9758 | 76.25% | 0.8836 | 73.26% |

**假设被证伪。** 播放分布特征在绝对热度口径下让模型**变差** 0.0061 AUC、0.92pp 召回；
在跃升口径下只带来 +0.0004 AUC / +0.38pp，落在种子抖动（±0.0003 AUC）的边缘。

原因不是「播放日志没用」，而是**覆盖率本身成了泄漏式的代理变量**：
`big_matrix` 只有 7,176 个采样用户，只能覆盖 20.3% 的「视频×日」。
于是「这条记录有没有 play 特征」≈「这个视频是否被采样用户看过」≈「它够不够热门」。
模型学的是这个缺失模式，不是内容质量。证据：只在覆盖子集上评估，G1 同样输给 G0
（0.9472 vs 0.9558）。两种设计得出一致结论，所以这个负结果是稳的。

**这条对我的意义比一个正结果大**：它说明「给模型更多数据」不等于「给模型更多信息」，
而判断这两者的差别，靠的是先想清楚缺失机制，而不是先跑一版看涨没涨。

## 5. 局限

- **单一平台、单一时间窗**：只有快手，2020 年 7–9 月共 63 天。结论不外推到跨平台。
- **「次日」不是严格次日**：`lead_days == 1` 只占 93.01%，最长间隔 179 天。
  严格口径的数字见 §4.5（AUC 掉 0.0012，方向不变），但**已提交的主表仍是旧口径**，
  正文与 `outputs/exp_eval_upgrade.json` 保持一致，两者不要混引。
- **冷启动样本默认不进模型**：`dropna` 删掉 9.81% 的样本，且删掉的恰是高信息量的一段
  （正样本率 33.41% vs 24.11%）。`--keep-na` 的数字见 §4.5，但主表未采用。
- **切分按特征日而非目标日**：7,105 行训练样本的标签落在测试窗口内，修正后 AUC 降 0.0054。
- **标签分位阈值用全期计算**：`label_abs` 的 75 分位在含测试期的样本上算，属轻微跨期泄漏。
  另外口径描述应为「当日**可预测样本**的前 25%」，不等于「当日全部活跃视频的前 25%」。
- **内容特征用整数编码**：`up_type_idx` / `tag_idx` 用 `category.cat.codes`，类别被压成一维乱序数轴，
  会低估内容属性的表达力。`0.5284` 这个数的正确读法是「在当前编码方式下无信号」，
  换 one-hot 后应复核（未做）。
- **播放日志特征受采样偏差限制**：`big_matrix` 只覆盖 20.3% 的视频×日，
  缺失模式与热度相关，因此 §4.6 的负结果**不能**推广成「播放行为对预测无用」，
  只能说「在当前采样下，以这种方式加入无用」。
- **无原始视频内容**：数据集只有元数据与内容标签，没有画面和文本，做不了多模态。
- **概率未校准**：AUC 只反映排序质量，没检验概率是否可信（Brier / 可靠性曲线未做）。
- **全部为离线评估**：没有线上 A/B，任何数字都不代表上线效果。

已做过的稳健性检验（`outputs/label_robustness.csv`）：

| 跃升标签定义 | 测试样本 | 正样本率 | 模型 AUC | 基线 AUC | 召回（模型 / 基线，全局口径） |
|---|---|---|---|---|---|
| 原始 2 倍阈值 | 92,735 | 7.60% | 0.8814 | 0.4265 | 72.67% / 8.20% |
| 最小量门槛 K=20 | 34,476 | 7.15% | 0.8993 | 0.3146 | 79.36% / 4.87% |
| 泊松显著性（+2σ） | 92,735 | 12.16% | 0.8909 | 0.6412 | 72.77% / 26.52% |

三种定义下模型都对基线保持大幅优势，说明结论不依赖某一个阈值。
**未做**的是 1.5× / 3× 连续阈值的敏感曲线。

## 6. 快速开始

```bash
# 1. 依赖（Python 3.11 / 3.13 验证通过，版本区间已锁定）
pip install -r requirements.txt

# 2. 数据：把两个原始文件放到 data/raw/（约 350 MB，见 data/README.md）
pip install huggingface_hub
huggingface-cli download hiiamkik/kuai-rec-data --repo-type dataset \
  --include "big_matrix.csv.gz" "item_daily_features.csv.gz" --local-dir data/raw

# 3. 数据库（推荐：容器化，端口已对齐 3307）
docker compose up -d
#   或者用已有的 MySQL：
#   mysql -h 127.0.0.1 -P 3307 -u root < sql/schema.sql

# 4. 一键复跑：清洗入库 → SQL 指标 → 建模 → 图表
export MYSQL_HOST=127.0.0.1 MYSQL_PORT=3307 MYSQL_USER=root MYSQL_PASSWORD=
python run_all.py

#   Windows cmd / PowerShell 用：
#   set MYSQL_HOST=127.0.0.1 && set MYSQL_PORT=3307 && set MYSQL_USER=root && set MYSQL_PASSWORD=

# 5. 延伸实验（只需 data/clean/*.csv，不需要数据库）
python experiments/eval_upgrade.py        # per-day 口径 + 精确率 + PR 曲线（本文主表来源）
python experiments/significance.py        # 1000 次按天 bootstrap + 5 种子 → 差值 CI
python experiments/ablation.py            # 八组特征消融
python experiments/strict_eval.py         # 四种口径审计（严格次日 / 冷启动 / 切分泄漏）
python experiments/playlog_features.py    # 播放日志分布特征（负结果，见 §4.6）
python experiments/breakout_experiment.py # 跃升标签 + 方向检验
python experiments/plot_ablation.py       # 只读 json 重新出图

# 6. 测试（不需要数据库和原始数据）
pytest -q
```

模型参数固定：XGBoost 500 棵、learning_rate 0.06、max_depth 6、subsample/colsample 0.9、`random_state=42`，
并发数统一由 `src/features.py` 的 `N_JOBS` 控制（可用环境变量覆盖）。

**关于可复现性，有两件事必须说清楚：**

1. **行顺序会影响结果。** XGBoost 的 `hist` 算法对训练数据的行顺序敏感：
   实测同一份数据、同一组超参，仅把行顺序从「原始顺序」换成「按 (d, video_id) 排序」，
   AUC 就从 0.980863 变成 0.981078。所以排序统一放进 `build_dataset()` 末尾做一次，
   任何消费方拿到的顺序都相同 —— 否则两个脚本会给出「同一件事」的两个数字。
2. **库版本会影响结果。** 本仓库早期提交的 `outputs/*.json` 是在较老的 xgboost 上生成的，
   在当前环境（xgboost 3.4.x）重跑，AUC 会有 ±0.0002 的系统性偏移。
   `requirements.txt` 现在锁了主版本区间，**跨大版本升级必须重跑并同步更新 README**。
   种子抖动（±0.0003）与这两者叠加，就是为什么「无增量」必须靠置信区间说，
   而不能靠眼看两个小数点。
